# Copeland Backend API Documentation

Frontend integration reference for the Copeland marketplace API.

## 1. API conventions

### Base URL

Use the deployed backend origin as `API_BASE_URL`.

- Health: `GET /health`
- Application API prefix: `/api`
- Webhooks are outside the API prefix: `/webhooks`

Example:

```ts
const response = await fetch(`${API_BASE_URL}/api/products`, {
  credentials: 'include',
});
```

### Authentication

Authentication is handled by Better Auth under `/api/auth/*`.

- Sessions use cookies.
- Frontend requests that depend on the signed-in user must send `credentials: 'include'`.
- Email/password authentication is enabled.
- Email verification is required before normal authenticated workflows.
- The user role is returned by the auth user/session payload and is one of: `buyer`, `supplier`, `shipping`, `staff`, `admin`.

The exact Better Auth endpoint payloads are generated by the installed Better Auth version. Frontends should use the Better Auth client or follow the auth endpoint contract for the deployed version rather than hardcoding undocumented fields.

### Content types

- JSON endpoints: `Content-Type: application/json`
- Paystack webhook: `Content-Type: application/json`; the server receives the raw body for signature verification.
- JSON body limit: 1 MB.

### Successful responses

The API usually returns the created, updated, or queried resource directly. Some operations return a wrapper:

```json
{
  "message": "Order created successfully. Ready for payment.",
  "order": {}
}
```

### Error responses

All application errors use this shape:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable explanation",
    "details": {}
  }
}
```

`details` is optional. Validation failures are normally HTTP `400`. Authentication and authorization failures are produced by the auth middleware and should be handled as `401` or `403`.

### Money and identifiers

- Amount fields ending in `Kobo` are integers in Nigerian kobo. Display naira by dividing by 100.
- IDs are UUID strings unless otherwise noted.
- Dates are returned as serialized ISO date strings.
- Do not trust client totals, prices, commission, or payout amounts; the backend calculates financial values.

## 4. Authentication

### `ALL /api/auth/*`

Better Auth owns the authentication routes. The frontend should use the Better Auth client for:

- Creating an account with name, email, and password.
- Signing in with email and password.
- Signing out.
- Reading the current session.
- Verifying an email address.
- Requesting and completing a password reset.

The backend sends verification, welcome, password-reset, and reset-confirmation emails. The role defaults to `buyer`; role changes are controlled by backend workflows and must not be supplied by an untrusted frontend.

Typical frontend behavior:

1. Submit sign-up.
2. Show an email-verification prompt.
3. Sign in after verification.
4. Fetch the session/user and route the user by role.
5. Send cookies on all protected requests.

## 5. Products

### `GET /api/products`

Returns live products for the public catalog.

Optional query parameters:

| Field | Type | Use |
|---|---|---|
| `q` | string | Search text |
| `category` | string | Category filter |
| `size` | string | Size filter |
| `label` | `true \| false` | Filter by Copeland label |
| `page` | number | Page number |
| `limit` | number | Page size |
| `minPrice` | number | Minimum price in kobo |
| `maxPrice` | number | Maximum price in kobo |

Success `200`: product list/pagination object returned by `ProductService.getLiveProducts`.

Frontend use: catalog pages, search, category filters, price filters, and pagination.

### `GET /api/products/:id`

Returns one live product.

Path:

- `id` — required product UUID.

Success `200`: product object.

Errors:

- `404 PRODUCT_NOT_FOUND` — product does not exist or is not live.

### `GET /api/products/mine`

Returns products owned by the signed-in approved supplier.

Required role: `supplier`.

Success `200`: supplier product list.

Common errors: unauthenticated, wrong role, or partner account not approved.

### `POST /api/products`

Creates a supplier product.

Required role: approved `supplier`.

Required body:

```json
{
  "name": "Product name",
  "description": "Product description",
  "category": "Category",
  "priceKobo": 250000
}
```

Optional body fields:

| Field | Type/constraints |
|---|---|
| `moq` | positive integer |
| `quantityAvailable` | non-negative integer |
| `colours` | array of non-empty strings, max 50 chars each |
| `sizes` | array of non-empty strings, max 50 chars each |
| `images` | array of valid URLs, max 30 |
| `tier` | string, max 50 chars |
| `inventory` | max 500 variants; each variant has optional `size`, optional `colour`, and required non-negative integer `quantityAvailable` |

Success `201`: created product.

Error: `400 PRODUCT_CREATE_FAILED`.

### `PATCH /api/products/:id`

Updates a supplier-owned product.

Required role: approved `supplier`.

Body: at least one of `name`, `description`, `category`, `priceKobo`, `moq`, `quantityAvailable`, `colours`, `sizes`, `images`, or `tier`. Field rules match product creation.

Success `200`: updated product.

Errors:

- `400 PRODUCT_UPDATE_FAILED`
- Validation error when no update field is supplied.

### `POST /api/products/:id/submit`

Submits a supplier product for moderation.

Required role: approved `supplier`.

Success `200`: updated product.

Error: `400 PRODUCT_SUBMISSION_FAILED`.

### `POST /api/products/:id/moderate`

Moderates a submitted product.

Required role: `admin` or `staff`. Only `admin` may use `badge`.

Body:

```json
{
  "action": "approve",
  "reason": "Optional explanation"
}
```

`action` must be one of: `approve`, `reject`, `changes_requested`, `pause`, `badge`.

Success `200`: updated product.

Errors:

- `403 FORBIDDEN` — non-admin attempted `badge`.
- `400 PRODUCT_MODERATION_FAILED`.
- `400 INVALID_MODERATION_ACTION` — action missing.

## 6. Orders and checkout

### `POST /api/orders/checkout`

Creates a pending-payment order and reserves stock.

Public endpoint. Rate limited.

Required body:

```json
{
  "email": "buyer@example.com",
  "items": [
    {
      "productId": "product-uuid",
      "quantity": 2
    }
  ]
}
```

Optional fields:

- `name` — string, 1–200 chars.
- `phone` — string, 5–40 chars.
- Item `size` — string, max 50 chars.
- Item `colour` — string, max 50 chars.

Item requirements:

- `productId` is a UUID.
- `quantity` is a positive integer.
- `items` contains 1–100 items.

Success `201`:

```json
{
  "message": "Order created successfully. Ready for payment.",
  "order": {}
}
```

Errors:

- `400 INVALID_CHECKOUT` — email or items array missing.
- `400 CHECKOUT_FAILED` — unavailable product, insufficient stock, or order creation failure.

Frontend use: submit checkout details, save the returned order ID, then call the payment initialization route.

### `POST /api/orders/:id/pay`

Initializes a Paystack payment for an order.

Public endpoint; the order/payment service validates the order server-side.

Path:

- `id` — required order UUID.

Success `200`:

```json
{
  "message": "Payment initialized. Redirect buyer to this URL.",
  "paymentData": {}
}
```

The frontend should use the payment URL/reference supplied in `paymentData`; it must not calculate or override the amount.

Error: `400 PAYMENT_INITIALIZATION_FAILED`.

### `POST /api/orders/:id/cancel`

Cancels a pending guest order and releases stock.

Required body:

```json
{ "email": "buyer@example.com" }
```

Success `200`:

```json
{ "message": "Order cancelled and stock released" }
```

Errors:

- `400 INVALID_CANCELLATION`
- `400 ORDER_CANCELLATION_FAILED`
- `409 ORDER_NOT_CANCELLABLE`

### `POST /api/orders/lookup`

Looks up a guest order using order number and buyer email.

Required body:

```json
{
  "orderNumber": "ORD-123",
  "email": "buyer@example.com"
}
```

Success `200`: order object.

Errors:

- `404 ORDER_NOT_FOUND`
- `400 INVALID_ORDER_LOOKUP`
- `400 ORDER_LOOKUP_FAILED`

### `GET /api/orders/supplier`

Returns orders/items relevant to the signed-in supplier.

Required role: approved `supplier`.

Success `200`: supplier order list.

### `PATCH /api/orders/:orderId/items/:orderItemId/fulfillment`

Updates item fulfillment status.

Required role: approved `supplier`.

Body:

```json

```

Allowed statuses: `packed`, `shipped`, `delivered`.

Success `200`: updated order item.

Errors: `400 INVALID_FULFILLMENT_STATUS` or `400 FULFILLMENT_UPDATE_FAILED`.

### `PUT /api/orders/:orderId/shipping-partner`

Assigns a shipping partner to an order.

Required role: `admin` or `staff`.

Body:


## 12. Paystack webhook

### `POST /webhooks/paystack`

Receives Paystack payment and transfer events. This route is called by Paystack, not by the browser.

Required header:

- `x-paystack-signature` — HMAC-SHA512 signature of the exact raw request body using the Paystack secret.

Required event fields:

```json
{
  "event": "charge.success",
  "data": {
    "id": 123,
    "reference": "payment-reference"
  }
}
```

Supported event behavior:

- `charge.success` — verifies the transaction with Paystack, marks the order paid when amount/currency/state match, creates payout and ledger records, and sends confirmation email.
- `transfer.success` — marks payout success and may complete the order.
- `transfer.failed` — marks an initiated payout failed.
- `transfer.reversed` — marks a successful payout reversed.

Success: HTTP `200` with an empty response body.

Errors:

- `400 INVALID_WEBHOOK` — missing configuration/body, invalid JSON, or missing event/reference.
- `401 INVALID_SIGNATURE` — signature mismatch.
- `502 PAYMENT_VERIFICATION_FAILED` — Paystack verification failed.

The frontend should never call this endpoint directly.

## 13. Frontend error handling checklist

1. On `401`, refresh the auth/session state and redirect to sign-in when appropriate.
2. On `403`, show a permission message and do not retry unchanged.
3. On `400`, read `error.code` for field-level UI behavior and show `error.message` as the user-facing fallback.
4. On `404`, show a missing-resource state.
5. On `409`, explain that the resource changed state, such as an order no longer being cancellable.
6. On `429`, wait and retry only when the operation is safe and idempotent.
7. On `500` or `502`, show a generic retry/support message and avoid exposing server details.
8. Preserve the order ID, payment reference, and request context for payment support cases.

## 14. Recommended typed client wrapper

```ts
export type ApiError = {
  error: {
    code: string;
    message: string;
    details?: unknown;
  };
};

export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const response = await fetch(`${API_BASE_URL}${path}`, {
    ...init,
    credentials: 'include',
    headers: {
      'Content-Type': 'application/json',
      ...(init.headers ?? {}),
    },
  });

  const payload = await response.json().catch(() => null);
  if (!response.ok) {
    throw payload ?? {
      error: { code: 'HTTP_ERROR', message: `Request failed with ${response.status}` },
    } satisfies ApiError;
  }
  return payload as T;
}
```

For checkout, payment initialization, partner applications, and payout operations, disable duplicate submissions while a request is pending and display the backend error code/message when the request fails.

## 15. Authentication API: complete frontend reference

The backend mounts Better Auth at `/api/auth`. The routes below are the email/password and session routes enabled by this project. All examples assume:

```ts
const API_BASE_URL = 'https://api.example.com';

async function authRequest<T>(path: string, init: RequestInit = {}) {
  const response = await fetch(`${API_BASE_URL}/api/auth${path}`, {
    ...init,
    credentials: 'include',
    headers: {
      'Content-Type': 'application/json',
      ...(init.headers ?? {}),
    },
  });

  const body = await response.json().catch(() => null);
  if (!response.ok) throw { status: response.status, body };
  return body as T;
}
```

Never store the session token in localStorage or send a password to any endpoint other than the auth API. The browser stores the secure session cookie. Always use `credentials: 'include'`, including for `GET /api/auth/get-session`.

### Auth route summary

| Method | Route | Authentication | Frontend use |
|---|---|---|---|
| POST | `/api/auth/sign-up/email` | Public | Create an account |
| POST | `/api/auth/sign-in/email` | Public | Sign in |
| POST | `/api/auth/sign-out` | Session | Sign out |
| GET | `/api/auth/get-session` | Session optional | Restore the current user |
| POST | `/api/auth/send-verification-email` | Public | Resend verification email |
| GET | `/api/auth/verify-email?token=...` | Public | Consume email verification link |
| POST | `/api/auth/forget-password` | Public | Request reset email |
| POST | `/api/auth/reset-password` | Public | Set a new password |

Better Auth may include additional response metadata or headers in a patch release. Frontends should treat the documented fields below as the application contract and ignore unknown fields.

### `POST /api/auth/sign-up/email`

Creates a buyer account. Email verification is required before protected buyer, supplier, shipping, staff, or admin workflows can be used.

Required JSON body:

```json
{
  "name": "Ada Buyer",
  "email": "ada@example.com",
  "password": "A-long-password-123"
}
```

Field rules:

- `name`: required non-empty string.
- `email`: required valid email address; normalize user input to lowercase in the UI.
- `password`: required string; enforce a strong password in the UI. The server hashes it and never returns it.
- Do not send `role`; the backend sets the default role to `buyer` and rejects client-controlled role assignment.

Typical success: `200` or `201`, with the created user/session payload. A verification email is sent automatically. Show “Check your email to verify your account” rather than routing directly to protected pages.

Example:

```ts
await authRequest('/sign-up/email', {
  method: 'POST',
  body: JSON.stringify({ name, email, password }),
});
```

Common errors:

- `400` — invalid or incomplete fields.
- `422` — email already registered or password rejected by Better Auth validation.
- `429` — auth rate limit exceeded; wait before retrying.

### `POST /api/auth/sign-in/email`

Signs in with email and password and creates a cookie-backed session.

Required JSON body:

```json
{
  "email": "ada@example.com",
  "password": "A-long-password-123"
}
```

Optional body field:

- `callbackURL`: frontend URL to use after an auth redirect, when the frontend uses redirect-based handling.

Example:

```ts
await authRequest('/sign-in/email', {
  method: 'POST',
  body: JSON.stringify({ email, password }),
});
const session = await authRequest('/get-session');
```

Success returns the authenticated user/session information and sets a session cookie. The user object includes `id`, `name`, `email`, `emailVerified`, and `role` when available. Roles are `buyer`, `supplier`, `shipping`, `staff`, or `admin`.

Common errors:

- `401` — invalid email/password.
- `403` — email verification is required; show a resend-verification action.
- `429` — too many sign-in attempts.

### `POST /api/auth/sign-out`

Ends the current session and clears the session cookie.

No request body is required:

```ts
await authRequest('/sign-out', { method: 'POST' });
// Clear frontend memory and navigate to /login.
```

Success is normally `200` with a success response or an empty JSON object. Treat an already-expired session as signed out. Common errors are `401` for a missing/expired session and `429` for rate limiting.

### `GET /api/auth/get-session`

Restores the current session after page load or refresh.

```ts
const session = await authRequest<{
  user: {
    id: string;
    name: string;
    email: string;
    emailVerified: boolean;
    role: 'buyer' | 'supplier' | 'shipping' | 'staff' | 'admin';
  };
  session: { id: string; expiresAt: string };
}>('/get-session');
```

Success returns `{ user, session }`. When there is no valid cookie, the response is commonly `200` with `null` or `401`, depending on Better Auth response handling. Treat either as unauthenticated; do not display a server error.

Use the returned role to select the dashboard. Do not assume that a role implies partner approval; supplier and shipping actions additionally require an approved partner account.

### `POST /api/auth/send-verification-email`

Resends the verification email. Use this after sign-up or when sign-in reports that verification is required.

Required JSON body:

```json
{
  "email": "ada@example.com",
  "callbackURL": "https://app.example.com/email-verified"
}
```

`callbackURL` is the frontend destination after the user clicks the email link and must be an allowed frontend origin. The endpoint should return a generic success response even when the account does not exist, so the UI should always show the same message: “If an account exists, a verification email has been sent.”

Common errors: `400` for invalid email/callback URL and `429` for too many requests.

### `GET /api/auth/verify-email?token=...`

Consumes the one-time token from the verification email. This is normally opened by the browser, not called with JSON.

Frontend route example:

```ts
const params = new URLSearchParams(window.location.search);
await fetch(`${API_BASE_URL}/api/auth/verify-email?${params}`, {
  credentials: 'include',
});
```

Success: the email is marked verified and the user can sign in. Redirect to the frontend’s verified-success screen. Common errors are `400` for a missing/malformed token and `401` or `410` for an expired or already-used token. Provide a “Send verification email again” action rather than retrying the same token.

### `POST /api/auth/forget-password`

Requests a password-reset email. The endpoint should not reveal whether an email exists.

Required JSON body:

```json
{
  "email": "ada@example.com",
  "redirectTo": "https://app.example.com/reset-password"
}
```

`redirectTo` must be an allowed frontend origin. Always show the same confirmation message, such as “If an account exists, check your email for a reset link.” Common errors are `400` for invalid input and `429` for repeated requests.

### `POST /api/auth/reset-password`

Sets a new password using the token from the reset link.

Required JSON body:

```json
{
  "newPassword": "A-new-strong-password-456",
  "token": "reset-token-from-email"
}
```

After success, send the user to sign-in rather than assuming they are signed in. The backend sends a password-reset confirmation email.

Common errors:

- `400` — missing token/password or invalid password.
- `401` or `410` — expired, invalid, or already-used token.
- `429` — too many reset attempts.

### Recommended auth state flow

1. On application start, call `GET /api/auth/get-session`.
2. If the result is unauthenticated, show public pages or redirect protected routes to `/login`.
3. On sign-up, show the verification-pending screen.
4. On sign-in, handle the unverified-email response with a resend button.
5. After sign-in, fetch the session and route by `user.role`.
6. For every protected API call, include `credentials: 'include'`.
7. On `401`, refresh session state once and redirect to sign-in if still unauthenticated.
8. On `403`, show a permission or partner-approval message; do not repeatedly retry.
9. On sign-out, clear cached user data and return to the public site.

### Auth error handling example

```ts
try {
  await authRequest('/sign-in/email', {
    method: 'POST',
    body: JSON.stringify({ email, password }),
  });
} catch (failure) {
  const error = failure as { status?: number; body?: { message?: string; error?: { message?: string } } };
  const message = error.body?.error?.message ?? error.body?.message;

  if (error.status === 401) showFieldError('email', 'Email or password is incorrect.');
  else if (error.status === 403) showVerificationPrompt();
  else if (error.status === 429) showMessage('Too many attempts. Please try again later.');
  else showMessage(message ?? 'Unable to sign in. Please try again.');
}
```

## 16. Frontend implementation notes

- The backend CORS policy only permits origins configured in `FRONTEND_ORIGINS`; browser requests from an unapproved origin fail before reaching a route.
- Cookies must be sent cross-origin with `credentials: 'include'`; the frontend fetch wrapper should set this centrally.
- Auth, checkout, application, and webhook-related endpoints are rate limited. Disable buttons while requests are pending.
- Never trust client-provided prices, totals, roles, commission values, payout values, or approval status.
- Keep payment references and order IDs available for support, but do not expose server secrets or Paystack secret keys.
